FIRST RELEASE GUIDE

From installation to recovery.

This is an engineering pilot. Use a dedicated Ubuntu Server 24.04 x86-64 test VM and disposable files until your own installation, reboot, backup and separate-host restoration checks pass.

1. Prepare the host

Use the package’s install.sh from a local or SSH terminal. It asks for two already mounted storage locations, an application hostname and a private management IP. It never partitions or formats disks. The installer starts the management console; it does not silently deploy your cloud.

2. Establish trusted management access

Use the root CA certificate exported by the installer and verify it over a trusted channel, or use a private HTTPS reverse proxy. Follow docs/ACCESS.md. Do not publish the management interface or enable public tunneling. Sign in through the advanced console and enable two-factor authentication, then bookmark /cloudops/.

3. Deploy and finish native AIO setup

Choose “Install cloud,” review the confirmation, and wait for the operation. Open AIO using its private setup address. Follow its documented first-run certificate and passphrase instructions. The application itself needs a real hostname and correctly trusted HTTPS. A host-side proxy must forward application traffic to 127.0.0.1:11000.

4. Configure and prove the first backup

In AIO, configure the exact backup directory chosen in the installer and complete the first native backup. Keep the Borg passphrase outside this cloud. Then use “Back up now” here. CloudOps records success only after fresh Borg completion and archive evidence. “Check backup integrity” is a separate check, not proof of restoration.

5. Test actual recovery

Create the optional dedicated probe account and run sudo cloudctl probe-credentials, then sudo cloudctl probe-enroll. Create another verified backup after enrollment. Export the non-secret recovery kit and securely preserve the separate probe credential. Follow docs/RECOVERY.md on a distinct, isolated recovery-test host. Import the original manifest, restore through AIO, and select “Verify recovered files.” That check validates one seeded file and anonymous access denial, not every document or sharing rule.

6. Schedule carefully and maintain one authority

After a verified backup, disable AIO’s native daily schedule before enabling the CloudOps host timer with sudo cloudctl enable-backup-timer. Do not enable two competing schedules. Updates and destructive recovery remain guided native AIO operations in this release.

When an operation needs attention

A closed browser does not cancel the host job. A reboot, executor failure or migration interruption is different. Inspect the activity output, AIO and sudo cloudctl history. Never repeatedly click an operation or downgrade an image to “undo” a migration. Root-only acknowledgement can unblock a failed operation after inspection; it does not mark the operation successful.

Extending your platform

ownCloud Infinite Scale, ownCloud Server and OxiCloud have reserved provider interfaces but are not implemented yet. A provider change is a migration, not an image swap. See docs/PROVIDER_CONTRACT.md and docs/ROADMAP.md in the package.
